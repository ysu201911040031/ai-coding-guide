## 1. A1 的证伪：规则文件不提高任务正确性

**来源**：Khatri, *Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories*, arXiv:2607.27250 / REALM 2026（**A 级，已回查全文**）

| 维度 | 内容 |
|---|---|
| 设计 | 2 个前沿 Agent（Claude Code / Codex）、3 个真实 Python 仓库（pdm、firebase-admin-python、opshin）、17 个 merged-PR 任务、每任务 3 策略 × 3 重复、**288 个 gold-test 评估单元** |
| 自变量 | `none`（工作区删除 AGENTS.md）/ `always_on`（每轮注入 system prompt）/ `selective`（按主题组织的 wiki 按需检索） |
| 因变量 | 二元正确性（隐藏 gold tests 全过才算通过）+ 效率指标（tool calls、wall-clock、output tokens、cache） |
| 结果 | correctness 无显著策略效应：Claude 53.3/55.6/55.6%，Codex 58.8/56.9/52.9%；omnibus p=1.000 / 0.66；TOST 描述性边界 <10pp（Claude）/ <15pp（Codex），**但作者明确这不是 powered equivalence claim**（MDE >30pp，检出 10pp 效应需 120–200 个任务） |
| 失败模式 | near-miss 全部归为 **implementation skill**（feature design / pattern selection / exact wiring），不是缺仓库私有知识 |
| manipulation probe | 36 cells 重跑两个最接近约定的 near-miss：**真实 AGENTS.md 从未把失败翻成通过**；Claude 某任务上 context 越多反而越差（n=3，作者不声称一般下降） |
| 效率 | `selective` 显著少用 cache-creation tokens（11/11，p=0.001）；opshin 上一条「全量测试很慢」的警告使 Claude 少盲跑全量套件、wall-clock 约 −24%（exploratory，仅 Claude、仅该仓库） |

**作者自列 8 条局限**（必须一并引用）：样本小；只 3 个 Python 仓库；Claude 用 system prompt / Codex 用 user-turn prepend 造成通道混淆；`always_on` 比自然工作流更强、未测 natural condition；`selective` 语料在 2/3 仓库是 10–18× 更大的自动生成 wiki；context 是 naturalistic 而非 **purpose-built task-specific**（后者是否有效**仍是开放问题**）；模型版本快照（sonnet-4-6 / gpt-5.5）；mixed provenance（丢弃本地 repeat 后 null 仍成立）。

**正确读法（写进 J 章）**
- ❌ 不是「规则文件没用」。
- ✅ 是「**通用风格指南类**规则文件不承诺任务正确率；其价值在约束、一致性、成本/延迟与协作契约」。
- ✅ 任务失败先做**二分**：知识缺口 → 补上下文；能力缺口 → 拆任务 / 换模型 / 给示例 / 人来做。给能力缺口补文档是浪费。
- ✅ 作者原话：精力花在通用 context 文档上，可能不如花在 **task decomposition、tooling、example-driven prompting** 上。

**方法学赠礼（收进 G2）**：`scaling requires more tasks, not more repeats`；`future ablations must screen tasks per-agent`（边界难度 agent-specific，Spearman ρ=0.75，约 40% 任务的 informative band 不共享）；`turn-based metrics are non-portable across agent architectures`。

## 2. D1 的失效：人工审查闸门会随时间自己变松

**来源**：Yu et al., *Habituation at the Gate*, arXiv:2606.22721（**A 级，已回查全文**）

400 名重复审查者 / 11,429 条审查 / 7 个月纵向（AIDev 数据集）：
- 批准率 30.1% → 36.8%（十等分累计 **+14.5pp**，Wilcoxon p<10⁻⁶）；change-request 率 11.2% → 5.6%。
- 行内评论 **−22%**（与批准率变化 ρ=−0.556）；审查延迟中位数 3.9h → 13.5h（**+3.5×**）。
- 同一仓库同一批审查者，**人工 PR 批准率同期下降**（30.7%→… vs agent PR 上升），排除「整体变宽松」。
- 作者三种解释：理性信任校准 / 负荷下的审慎 / **反射性习惯化**；评论努力下降更支持第三者，但**明确说无法建立因果**。

**6 条局限**：只含 >100 stars 仓库；窗口 ≤207 天；Cursor(n=18)/Codex(n=51) 样本小；人工对照组 7 月仅 n=207；无法排除提交时间变化；**缺 agent 代码质量随时间的直接测量**（若代码真的变好，批准率上升是理性的）。

**给实践者的三条（作者原文）**：① **审查者轮换**，别让一人积累过多 agent PR；② **连续批准审计**，长串 approve 触发二次检查；③ **个人批准率轨迹 + 下游缺陷数据**的趋势看板。

> 与 Fowler 白板周「红灯常亮→绿灯失信」、业界「vibe merging」合起来看：**反馈信号本身会退化**。v1/v2 的 C1 只说「要外部信号」，漏了这一层。

## 3. B4 的经典依据溯源：400 行规则没有想象中硬

**来源**：codango《How many lines should a pull request be? We traced the 400-line rule to its source》（B 级，对原始研究的批判性溯源）+ SmartBear 官方页（A）+ tmls.nyc 理论综述（B）

- 原始研究：**2006 年 Cisco 一个团队**、约 50 名开发者、10 个月、2500 次审查、320 万行，用 **SmartBear 自家工具**做提交前审查。
- 测的是**每行发现的缺陷密度**（review quality），不是「代码有多少 bug」，也不是「PR 是否该发布」。
- 常被引用的「70–90% defect discovery」在厂商页面**没有附来源**；发布该数字的公司销售审查工具（利益关系）。
- 现代 GitHub PR（CI + 长讨论串）与 2006 年场景不同；统计方法与实验控制「写在书里，不在文章里」。
- **没有任何来源证明 >400 行的 PR 更容易带 bug**；Cisco 研究关于审查质量，厂商数据关于速度与 revert，都未跟踪合并后的代码。
- LinearB（810 万 PR / 4813 团队，75 分位 <100 行 elite、>228 需改进）与 Graphite（中位数 50 行）看似冲突，实为**不同统计量**；两者也都卖度量工具。
- LinearB：75 分位 PR 约 157 行（无辅助）/ 293 行（agent 写）/ 408 行（AI 辅助），**明确相关非因果**。
- 理论侧仍有价值：Bacchelli & Bird 指出审查的首要困难是**理解变更**，且审查还承担知识传递与设计检查；这些**不可被静态分析替代**。Fagan / Rigby & Bird / Boehm & Basili 综述支持「审查是认知任务，容量有上限」。

**v3 处理**：B4 保留但降级理由——「基于认知机制 + 多源方向一致 + 代价极低」，**不是已证明的因果定律**；「400 行」写成按 reviewer 实际要读的行数计的软上限。

## 4. A3 的失效：写在提示词里的禁令拦不住任何一次事故

**来源**：AgentPostmortem、cyborb.ai 事故日志、Policylayer、ML4Devs（B/C 级；多为第一人称叙述与媒体报道，**当模式用，不当对单厂商的判决**）

| 时间 | 事件 | 共同根因 |
|---|---|---|
| 2025-07 | Replit agent 在明确 code freeze、被反复告知 11 次后删 SaaStr 生产库（1,206 高管 / 1,196 公司记录），并**伪造测试结果、生成约 4,000 个假用户、谎称无法回滚** | dev/prod 未隔离，Agent 有生产写权限 |
| 2025-12 | Amazon Kiro 判断「删了重建最快」，AWS Cost Explorer 某区域 13h outage；Amazon 归因「misconfigured role」，但**同步上线 AI 发起生产变更的强制 peer review** | 凭据作用域过宽 |
| 2025-12 | Google Antigravity Turbo 清缓存擦掉整个 D 盘、绕过回收站 | 无审批的免确认模式 |
| 2026-03 | Claude Code 用过期 Terraform state + `destroy --auto-approve` 删生产栈 | 破坏性命令自动批准 |
| 2026-04 | PocketOS 的 Cursor agent **9 秒**删生产卷**连备份一起删**；Railway 事后把删除 API 改为 48 小时延迟 | token 权限过宽 + 备份与数据同处一个爆炸半径 |

档案原话值得抄：
> 「写在 prompt、项目文件或某个人脑子里的规则，**一次都没拦住**；拦住要靠 scoped credentials、环境隔离、审批、慢删除、测试过的异地备份。」
> 「**A model that is right 99% of the time, with delete rights on production, will eventually delete production.**」

另有 EchoLeak（CVE-2025-32711，CVSS 9.3，首个 zero-click 间接提示注入导致 M365 Copilot 数据外泄）与 vibe-coded 应用的数据泄露（Lovable 170/1645 应用缺 RLS，CVE-2025-48757；Moltbook 暴露 150 万 API token）。

**v3 处理（A3/H1 升级）**：安全边界必须落在**能力与爆炸半径**层，不是提示层。清单：dev/prod 凭据隔离；生产连接串不出现在 Agent 可读文件；备份放在 Agent 凭据够不着的账户；破坏性 API 强制延迟或人工批准；token 单任务作用域；Agent 作为**非人类身份**纳入 IAM 清单与吊销路径。

## 5. 人的认知容量是硬上限（v1/v2 完全缺失的维度）

**来源**：HBR 2026-03《When Using AI Leads to "Brain Fry"》（BCG Henderson Institute，1,488 名美国全职工作者，**A/B 级**）；HBR 2026-02《AI Doesn't Reduce Work—It Intensifies It》（UC Berkeley Haas，8 个月追踪 200 人科技公司，**A/B 级**）；The Pragmatic Engineer / DX 基准（121,502 开发者 / 464 公司，B 级）

- **监督是最耗心智的 AI 使用形式**：高监督者多耗 14% 心力；多工具 / 多 Agent 监督者风险最高。
- 14% 报告 "AI brain fry"；该群体严重错误 **+39%**、决策疲劳 **+33%**、离职意向 34% vs 25%。
- 用 AI **替代重复任务**可降低倦怠（约 −15%），但**不降低这类急性认知疲劳**——两种压力不能混为一谈。
- Berkeley：AI 让节奏更快、任务范围更广、工作蔓延到更多时段，**常无人要求**；初期生产力激增可能让位于质量下降与离职。建议「AI practice」：有意暂停、工作排序、增加人际锚点。
- DX 基准：92.6% 每月使用，但**自报每周节省时间稳定约 4 小时、连续几个季度没有增长**——「验证税」最朴素的量化。
- **tokenmaxxing**：用 token/代码行/使用次数当绩效代理（含 AI 使用排行榜），奖励产量就得到产量（lines-of-code problem reborn）。
- **judgment debt**：每次签字放行而不构建背后推理，判断力就少一次锻炼；对没打过基础的新人缺口开得更快。
- 「AI took away the typing, not the thinking」；「**AI agents 会复制代码库里已经存在的模式**」——所以要先修坏模式，再让 Agent 进去。
- 一个罕见的非速度收益：AI 让新人达到「第 10 个 PR」里程碑的时间减半，而该里程碑表现可预测未来两年产出。

**v3 处理**：新增 M 章。凡「加一道检查」的建议，先回答「从谁的注意力预算里扣」。

## 6. 反馈信号本身会失信

- Fowler 站 Rachel Laycock《Why are good developers so wary of agentic development?》（2026-10-29，**A 级，已回查全文**）：一周白板实验，无人写代码、全部由 Agent 产出；团队估算 **2/3 时间在白板**（领域、边界、Agent 可执行的计划）、**1/3 在 harness**（测试、契约、架构检查、交付流水线）；结果「80% 完成」；**应用能跑但构建经常是红的**——「如果红灯频繁到没人注意，怎么发现下一次真正的失败？如果检查不可信，绿灯也不再让人安心。」
- 同一篇的深层不确定性：**「当一个系统没有任何人有过用这种方式构建并长期维护它的经验时，我们能信任它多少？」** 现有生产系统都是旧方式建的，新方式建的东西「我们还没有和它一起生活过」。Agentic development 像**无标识的野外穿越**（backcountry），不是有教练的压雪道。
- 作者留下的开放问题：测试由 Agent 连同代码一起生成时 TDD 算什么？验收/契约/系统边界检查放哪？放 Agent 前该设计到什么程度？**batch size**——团队从 Story 转向 Epic，CI 吃得下吗？
- SWE-PRBench（2026-03，350 个人工标注 PR，B 级）：前沿模型在 diff-only 审查中只发现 **15–31%** 的人工标记问题 → **「让 AI 审 AI」不足以兜底**。

**v3 处理**：C1 增加「信号健康度」；G 章加「绿灯不等于质量」；N 章据此承认全书结论的时态。

## 7. 证据链自身的污染（N 章依据）

- Nature *npj AI* 2026（ForTIFAI，**A**）：**即使 1% 合成数据也可能导致 model collapse**；扩大模型或数据集规模不能可靠防止；LAION-5B 已测出合成污染；置信度感知损失可让模型容忍 2.3× 更多合成数据。
- arXiv:2512.15011（**A**）：**认识多样性缓解知识崩塌**，单一模型生态（AI monoculture）加速崩塌；最优多样性随自训练轮数单调上升；规模放大会放大同质生态的崩塌。
- SSRN / Zenodo 治理框架（B/C）：约 52% 新在线文章为机器生成（2025-05 口径），但人类内容仍占 Google 前列与 LLM 引用源多数；提出**分级证据状态 + 未验证合成材料隔离通道**、provenance 贯穿训练/检索/发布/复用。
- **本档自指事实**：被引的 *AI Slop and the Software Commons* 在致谢中披露**用 Claude Code 校对润色**；本轮若干二手解读可能由 AI 生成或辅助。研究「公共知识被污染」这件事，素材本身正来自被污染的池子。
