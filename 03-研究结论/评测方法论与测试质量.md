# 研究结论④：评测方法论与测试质量（v2 新增）

> 归档日期：2026-11-11 ｜ 类别：研究结论
> 对应手册：G 章（G1–G4）、B1 的 TDM 修订、C2 修订
> **v1 的缺口**：引用了 SWE-bench 等分数，却没讨论分数本身可不可信。

---

## 1. 为什么这一章必要

v1 用 SWE-agent / Agentless 的分数论证「harness 比模型更影响结果」。这个论证方向成立，但**分数的可比性**没被审视。2025–2026 年的公开材料显示，编码 Agent 的榜单分数受至少四类因素干扰：数据污染、测试套件缺陷、scaffold 差异、自报无复现。对工程团队的实际含义是：**不要用公开榜单分数决定生产工具选型，要用自己的私域任务集做回归**。

## 2. 四类干扰

### 2.1 数据污染（contamination）

- SWE-bench 原始任务 **超过 94%** 在主流模型知识截止日之前提出（社区 wiki 汇总，C 级），存在 issue 讨论与修复代码进入预训练语料的风险。
- 有报道称 2025 年底 OpenAI 的审计发现，多个前沿模型在只给 Verified Task ID 时能复述 gold patch 片段；在部分难题上，「unsolvable as stated」与测试缺陷比例很高（C/B 级，具体比例不引用）。
- SWE-bench+ / OpenLM 的研究称，原始 benchmark 上约 **32.67%** 的成功补丁涉及 solution leakage（issue 或其评论里含解法或强提示）；过滤后 SWE-agent+GPT-4 的解决率从 12.47% 降到 3.97%（B/C 级，取**数量级**不取精确值）。
- 应对思路（抗污染三角）：**Pro**（更长任务 + held-out/商业仓库 + 统一 scaffold）、**SWE-rebench**（按月时间切分）、**SWE-bench Live**（持续刷新新 issue，Microsoft Research，NeurIPS 2025）。

> ⚠ 但 Pro 也非免疫：有报道称 2026 年对 Pro 公开子集的审计标记了相当比例的问题任务（过严测试、提示欠明确、覆盖不足）。**「更长 + 私有」本身不保证评测健全**。

### 2.2 测试套件本身有缺陷

- *Are "Solved Issues" in SWE-bench Really Solved Correctly?*（arXiv:2503.15223，B 级，经二手汇总核对）指出部分 Verified 实例的 test patch 不完整，允许错误或部分解法通过；UTBoost / PatchDiff 等工作认为榜单分数可能被抬高若干百分点。
- 测试太窄会拒绝功能正确的提交，太宽会要求 issue 里从未提及的功能。
- **这一条与 TestGenEval 的结论互相印证：验证器不可靠时，「通过测试」不等于「做对了」。**

### 2.3 Scaffold 方差

- 同一模型在不同 harness 下，SWE-bench Pro 分数可差约 **10 个百分点**（B 级汇总）；Terminal-Bench 类榜单把 model 与 harness 分列后也显示固定模型换 harness 的分数差可达数点。
- 官方 SWE-bench 后来推标准化 bash-only 轨道（mini-swe-agent），目的正是**让模型成为唯一变量**。
- 结论：看到「某模型 80%」必须追问 **哪个 scaffold、哪个数据分区、谁能复现**。社区汇总称 Verified 榜单曾有大量条目未独立复现（C 级）。

### 2.4 自报与饱和度

- 榜单多依赖自报；Verified 顶部模型分数聚集、区分度下降，而 Pro / Live 上的分数显著更低（方向一致，具体分数不引用）。
- 静态、公开、用久了的 benchmark 会饱和并被污染，这是结构性问题，**不是换个新榜单就能一劳永逸**。

## 3. 测试质量：覆盖率 ≠ 抓 bug 能力（A 级）

**TestGenEval**（Jain, Synnaeve, Rozière, **ICLR 2025**，官方页面 arXiv:2410.00752）
- 规模：基于 SWE-bench，**68,647 个测试 / 1,210 个 code-test 文件对 / 11 个维护良好的 Python 仓库**；覆盖「从零写测试」「补全测试套件」「提升覆盖率」三类任务；是当时唯一同时测 **mutation score** 的测试生成基准。
- 结果：最好的模型 GPT-4o 平均覆盖率 **35.2%**、最佳变异分数 **18.8%**；Llama 3.1 405B 为 35.0% / 16.4%。
- 最常见失败模式：**完全没有生成 assert 语句**，其次是断言错误与幻觉（NameError 等）；模型擅长「走到代码路径」，不擅长写出能抓细微 bug 的严格断言。
- 另一个反直觉发现：**冗长惩罚**——更大模型生成更冗长的测试套件，反而更容易因任一执行/语法错误导致整套失败。中等规模专用模型（Codestral 22B）All Pass@1 最高。
- 局限（作者自述）：文件级、无仓库级上下文；变异测试计算昂贵；只评单轮 0-shot，未评 agentic 多轮修断言。

**配套证据（B 级，经 `aidlc.io/research` 索引）**
| 来源 | 结论 |
|---|---|
| MUTGEN（IEEE TSE 2025–2026） | LLM 生成的测试可达「100% 覆盖率但仅 4% 变异分数」；把存活 mutant 回灌给模型能补上大部分差距 |
| Meta, *Mutation-Guided LLM-based Test Generation at Meta*（ACH, 2025-01） | 571 个生成的加固测试，**73% 被工程师接受**，因为每个测试都被证明能杀死特定 mutant，而不是「跑过就算」 |
| ISSTA 2026 复现（11 模型 / 101,000 测试） | 变异分数与真实 bug 检测强相关（**r = 0.86**）——**但仅对回归测试**；当被测代码本身已经是错的，相关性弱 |
| Chu et al., LLM 单元测试生成综述（2025-11，115 篇） | 覆盖率百分比单独不能证明测试质量，变异分数是补上这个缺口的手段 |

**最关键的一条工程推论**：
> **测试要从「验收标准」生成，不要从「实现」生成。** 若让 AI 照着已有实现写测试，它会把当前的错误行为固化成断言（v1 的 TDM 没有防住这一点）。

## 4. 由此得到的准则（对应手册 G 章）

| 编号 | 准则 | 优先级 |
|---|---|---|
| G1 | 不看单一榜单选工具；追问 benchmark / scaffold / 数据分区 / 复现方 | P1 |
| G2 | 建**私域回归任务集**（来自自己仓库的真实任务），换模型/换规则后复测 | **P0** |
| G3 | 测试有效性用「能否杀死 mutant / 能否复现已知缺陷」衡量，不用覆盖率 | P1 |
| G4 | 验收测试从验收标准写，不从实现写；禁止 AI 自己写测试又自己判通过 | **P0** |

配套操作：
- 每个 AI 生成的测试至少回答：「它在防哪个具体缺陷？如果这个缺陷被重新引入，它会失败吗？」
- 对 AI 生成的测试做一次变异抽样（哪怕手工改几处实现看测试是否变红）。
- 把「测试文件 / 认证路径的改动」列为高风险改动，单独标记（见治理档的 provenance 建议）。
