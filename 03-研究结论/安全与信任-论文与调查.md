> 归档日期：2026-11-11 ｜ 类别：研究结论

## 1. Perry et al., CCS 2023（A 级，已回查 PDF）

**标题**：*Do Users Write More Insecure Code with AI Assistants?*
**作者**：Neil Perry, Megha Srivastava, Deepak Kumar, Dan Boneh（Stanford / UCSD）
**出处**：Proceedings of the 2023 ACM SIGSAC Conference on Computer and Communications Security (CCS '23), DOI 10.1145/3576915.3623157；arXiv:2211.03622

**设计**：47 名参与者，5 项安全相关编程任务，跨 Python / JavaScript / C 三种语言；对照「有 AI 助手」与「无 AI 助手」。控制变量包括既往安全知识、编程经验、学生身份。

**核心发现（摘要原文要点）**
- 有 AI 助手的参与者**写出的代码显著更不安全**；5 项任务中有 4 项更差。
- **更糟的是**：有 AI 助手的参与者**更可能相信自己写的是安全代码** —— 工具带来了对安全缺陷的过度自信。
- 交互分析：在提示中给出明确任务指令、指定要用的函数声明、让助手专注写 helper function 的参与者，产出的代码更安全。
- **把 AI 先前的输出当作新提示反复迭代，会放大或复制安全问题**。
- 能清楚表达并恰当改写 prompt，对写出正确且安全的代码至关重要。

**对应用户手册**：D2（异常路径与前置条件）、D4（安全门禁）、C1（外部信号）、A4（规则要命令级——「写清楚函数声明/约束」）、B5（别把旧输出不断回灌）。

## 2. Pearce et al., IEEE S&P 2022（A 级，经多处一手引用佐证）

**标题**：*Asleep at the Keyboard? Assessing the Security of GitHub Copilot's Code Contributions*
**设计**：围绕 MITRE Top 25 CWE 构造 89 个场景，生成 1,689 个程序。
**结论**：约 **40%** 的生成程序含漏洞。
**地位**：早期被广泛引用的基线，说明「接受 AI 生成代码而不审查」的固有风险。

## 3. Veracode 2025 GenAI Code Security Report（A 级，官方页面）

**发布**：2025-07-30
**设计**：测试 **100+ 个 LLM**，覆盖 Java / Python / C# / JavaScript，80 项结构化编码任务，针对 SQL 注入（CWE-89）、XSS（CWE-79/80）、日志注入（CWE-117）、不安全加密算法（CWE-327）等。

**结果**
- **45%** 的代码样本未通过安全测试、引入 OWASP Top 10 漏洞。
- 分语言失败率：**Java 72%**、C# 45%、JavaScript 43%、Python 38%。
- **XSS 防护在 86% 的相关样本中失败**；日志注入相关失败约 88%（后者见二手汇总，C 级）。
- **最关键的一条**：模型在「语法正确 / 功能可用」上随规模和发布时间改善，但**安全表现持平**——「更聪明的模型不会自然带来更安全的代码」。

**官方建议**：不要因为用了 AI 就跳过扫描；把 SAST / 密钥扫描作为每个 AI 参与 PR 的门禁；盘点第三方、开源、外包代码中可能已存在的 AI 生成代码。

## 4. Spracklen et al., USENIX Security 2025（A 级，经研究索引页核对）

**标题**：*We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs*
**规模**：576,000 个样本、16 个模型。
**结论**：**19.7%** 的推荐包不存在，产生 **205,474** 个不同的幻觉包名；开源模型幻觉率约 21.7%，商业模型约 5.2%；**43% 的幻觉名在重复查询中反复出现**，使其可被抢注并利用（供应链攻击面）。

**对应手册 D5**：新增依赖/接口前逐个核对存在性、版本、许可；这不只是「编译不过」的问题，是安全入口。

## 6. 信任与过度自信（A 级）

- **Stack Overflow 2025**：仅 3.1% 高度信任 AI 准确性，46% 不信任；66% 受困于「几乎对」的代码；45.2% 认为调试 AI 代码更耗时；75.3% 在不信任 AI 答案时仍会找人。
- **DORA 2024**：39% 对 AI 生成代码「很少或完全不信任」；同时报告指出「信任直接驱动 AI 生产力」——信任越高，接受建议越多、提交变更越多、搜索信息越少。
- **DORA 2025**：信任悖论（24% 高信任 vs 30% 低信任），并把 AI 定位为「支持性工具而非人类判断的完全替代」。

**这里的张力值得注意**：信任不足会损失收益，过度信任会放大风险。手册的处理是 **「校准信任」而非「提高/降低信任」**——用可复核的验收标准（C2）和外部信号（C1）把信任锚定在证据上，而不是锚定在情绪或营销数字上。Perry 的「过度自信」发现正是这种校准必要性的实验证据。

## 7. 落地清单（手册 D4 的展开）

- [ ] 每个 AI 参与的 PR 强制 SAST + 密钥扫描 + 依赖检查，不通过不合并
- [ ] 语言感知规则覆盖 SQL 注入、输出编码、日志注入、弱加密、硬编码凭据
- [ ] 新增依赖逐个核对存在性 / 版本 / 许可（防包幻觉抢注）
- [ ] 对权限、支付、硬件控制路径逐条审异常分支与前置条件
- [ ] 禁止自动接受 / 自动合并 Agent 输出
- [ ] 盘点存量代码（含第三方与外包）中未扫描的 AI 生成部分
- [ ] 培训：明确告知「AI 辅助会提高过度自信」，安全敏感代码必须显式验证
