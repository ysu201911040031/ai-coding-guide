## 第一部分 · 多智能体的边界

### 1. 核心判断：加 Agent 不保证更好，方向由任务结构决定

**《Towards a Science of Scaling Agent Systems》**（Google Research / Google DeepMind / MIT，2025-12 首发，2026-04 v3；B 级，本轮未打开 arXiv 原文，经多份独立解读交叉确认）

- 规模：v1 约 180 个受控配置，v3 扩到 **260 个配置、5 类架构（单 agent / 独立 / 集中协调 / 去中心化 / 混合）、6 个 agentic benchmark、3 个模型家族**；工具、提示、token 预算标准化，只变协调结构。
- 结果区间：相对单 agent，加 agent 的效果从 **+80.8% 到 −70.0%**。
- 三类机制：
  1. **工具与协调权衡**：多 agent 摊薄每个 agent 的 token 预算，工具密集任务上每个 agent 都没有足够上下文去编排工具。
  2. **能力天花板**：单 agent 基线已高时，剩余收益很小，协调成本变成净损失（v1 估计阈值约 45% 单 agent 准确率，**v1 估计值不是固定规则**）。
  3. **误差放大**：独立 agent 把错误直接传进最终输出（**17.2×**），集中协调者校验子结果可降到 **4.4×**。
- 任务差异：顺序规划（PlanCraft）上所有多智能体变体下降 **39–70%**；可并行的金融处理任务上集中协调提升约 **80.8%**。
- 拟合模型能为 **87%** 的留出配置挑对架构（R² 约 0.37–0.41，预测力有限，别当选型神器）。

### 2. 其他独立研究（B/C 级，方向一致）

| 来源 | 结论 |
|---|---|
| **Anthropic**《How we built our multi-agent research system》(2025-06) | 多智能体研究系统比单 agent 高 **90.2%**，但同文披露：agent 约 4× token、多智能体约 **15× token**，且 **token 用量单独解释 80% 性能方差**（三因素合计 95%）。→ 诚实的问题不是「多 agent 是否胜过单 agent」，而是「是否胜过一个被允许思考/检索 15 倍久的单 agent」 |
| **Cognition**《Don't Build Multi-Agents》(2025-06-12) | 两条原则：① 共享完整 agent traces，不只共享消息；② **动作携带隐式决策，冲突的决策产生坏结果**。2026-04 更新规则：「**writes stay single-threaded，额外 agent 贡献智能而非动作**」 |
| **CooperBench**（Stanford / SAP Labs, 2026） | 两个 coding agent 编辑共享文件时，任务成功率约从 **50% 掉到 25%** |
| **Xu et al., ICLR 2026** | 同构多智能体在 HumanEval/MBPP/GSM8K 上与单 agent 几乎持平（92.1% vs 91.6% 等），成本高约 30% |
| **Salesforce Research 等**（2026-06） | 自动设计出的多智能体系统持续不如单模型 self-consistency，成本最高 **10×** |
| **Vals AI**（2026-10） | 团队成本 1.8–5.1×，四组团队配置中只有一组显著优于单 agent |
| **Cemri et al.**（UC Berkeley / MIT, 2025） | 1600+ 执行轨迹、7 个框架、**14 种失败模式**，归为系统设计缺陷 / agent 失配 / 任务验证失败三类；「bag of agents」里第一个 agent 的错误会污染下一个的上下文并逐级放大 |
| **Tang et al. 2025**（任务复杂度） | 多智能体收益随任务 **depth（顺序推理步数）与 width（所需能力种类）** 增长；简单任务上单 agent 持平或更好 |

### 3. 可操作的决策规则（写进手册 B7）

> **默认单 agent。加第二个 agent 之前，必须用它自己的 eval 证明它赢过「一个配置良好的单 agent」——而不是赢过直觉。**

- ✅ 适合并行：**读密集、子任务真正独立、只读探索、独立审查**（Anthropic research、Cognition 的「贡献智能而非动作」、集中式协调 + 结果校验）。
- ❌ 不适合：**写共享状态、顺序规划、工具密集、单 agent 基线已经很高、无最终验证器**。
- 必测三件事（来自 Google 研究的效率指标）：单 agent 基线成功率、**每个成功任务的 token 成本**（失败也要算）、错误如何在 agent 间传播。
- 必须集中校验：把独立 agent 的输出交给一个 coordinator/验证器再合并（把误差放大从 17.2× 压到 4.4×）。
- 成本估算起步数量级：多智能体约 **15× token**（Anthropic 生产数据），别只比墙钟时间。

> Anthropic 与 Cognition 看似矛盾的结论其实不冲突：**研究（read-only）适合并行，编码（write-heavy）不适合**。区分维度是「是否写共享状态」，不是「谁家的架构更先进」。

## 第二部分 · 治理与外部性

### 4. AI Slop 与公地悲剧（arXiv:2604.16754，A 级论文但为 **position paper**，已回查全文）

**核心论点**：AI slop 便宜生成、昂贵审查，而审查层本就薄弱；个体获得产出量/贡献数/速度的私人收益，成本外溢到协作式软件工程依赖的共享资源 —— 构成 **tragedy of the commons**。

**五类外部性**：reviewer capacity、codebase integrity、public knowledge resources、collaborative trust、**talent pipeline**（十年后还有没有能审查的人）。

**证据性质（必须标注）**：本文是立场论证（"we argue"），实证基础是 companion study 对 Reddit / Hacker News 中 **1,154 帖 / 15 个讨论串**的话语分析；**全文没有作者明确声明的 limitations 小节**，因此不能当因果证据。文中引用的实例（curl 关闭 HackerOne bug bounty、Ghostty 禁止 AI 贡献、tldraw 关闭外部 PR、GitHub「Eternal September of Open Source」等）来自公开事件，但比例数字多为社区/媒体口径，**只作现象，不作统计**。

**两个值得记住的判断**：
- 「**When the metric is volume, the output is slop.**」（指标是产量时，产出就是 slop）
- 「**generation without review is extraction**」（无审查的生成是抽取）
- 以及一个反直觉观察：curl 后来 AI slop 报告减少，但**高质量的 AI 辅助安全报告以空前频率涌入，维护者负载依旧** —— *quality improved; workload had not*。

### 5. Ostrom 八原则映射到软件工程（论文给出的处方）

| Ostrom 原则 | 论文的具体建议 |
|---|---|
| 清晰边界 | **provenance 做成默认属性而非可选项**：每个 artifact 带 metadata，标明模型产出了什么、人改了什么、哪些完全未借助 |
| 规则与本地条件一致 | **把 volume / velocity / 「AI 使用度」指标换成下游成本指标**：review effort、defect rate、rework time、post-merge incidents |
| 集体选择安排 | 让承担后果的开发者参与制定规范；被认可的心智是「**it is not AI's code, it is my code**」 |
| 监测 | AI 输出**默认可审**：provenance 标记、置信信号、对测试/认证路径等高风险改动打标、输出组织成可增量检视的形式而不是「一堵 diff 墙」 |
| 分级制裁 | 首次要求贡献者**逐行讲解代码**，重复低质量提交则失去合并权限，未达 review-readiness 的 PR 直接关闭而非陪着打磨 |
| 争议解决 | contributing guide 写明 reviewer 何时可拒绝 PR、AI 引入 regression 的归属、审批前有权要求 walkthrough |
| 组织权 | 社区可自定义 slop policy（含直接拒绝 AI 生成 PR） |
| 嵌套治理 | 工具开发者 / 团队负责人 / 组织 / 教育者四层必须协同，单点改进无效 |

**教育侧**：区分「必须学生独立展示」与「可委托给模型」的任务；用口试、live coding、提交物 walkthrough 作为不可委托的理解证明；早期课程限制 AI 工具，以培养日后安全使用 AI 所需的判断力。

### 6. 仓库健康记分卡（B 级，来自 luismori.dev 的六维度框架）

**不要试图检测「代码看起来像 AI 写的」**——人机混合作者使这不可靠。改为测结果，且**六个维度并列、不折成一个分数**：

| 维度 | 起始指标 |
|---|---|
| Correctness | change-fail rate、escaped defects、reverts、hotfixes |
| Maintainability | 新增重复、30 天重写率、变更函数复杂度、架构违规 |
| Review cost | PR 体积与扩散度、首次评审延迟、修订轮次、评审耗时 |
| Security | 按严重度的新增发现、暴露密钥、易受攻击依赖、发现存活时长 |
| Ownership | 独立评审覆盖、关键模块双 owner、孤儿模块 |
| Externalities | 新增依赖数、CI 分钟数、产物体积、算力增量、下游破坏 |

**必须把「交付价值」并列放在风险画像旁边**（完成的产品成果、吞吐量、端到端 lead time），因为更有价值的工作本来就可能消耗更多 CI / 评审 / 算力。且记分卡**只能显示变化，不能解释原因**；要测因果需分阶段 rollout、随机设计或控制任务混合的前后对照。

### 7. DORA 2026 的指标口径（C 级转述，待回查）

- DORA 2026-03 指引把成本命名为 **verification tax**：「生成阶段省下的时间常被重新分配到 verification overhead 与 prompting overhead」。
- 同一指引要求**停止依赖 output-based metrics**（代码行数、license 数、token 数、原始 PR 数），因为 AI 会把它们全部 inflate。
- 值得每周盯的早期信号：PR 体积（batch size）、等待评审时长、价值流各阶段停留时间、rework rate、非工作时间提交（倦怠信号）。
- 「J-curve」说法（生产力先降后升）亦来自该时期的二手汇总，**未回查原文，不作硬结论**。
