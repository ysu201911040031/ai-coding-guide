## 2. 合并后的工作流：四条车道

> 原来的五套流程合并成一张表。**先选车道，再决定写不写卡**；卡只有一种（`07-一键落地/templates/任务卡-四车道.md`）。

| 车道 | 触发条件 | 产出 | 验收 | 审查 |
|---|---|---|---|---|
| **L0 小改** | 单文件、需求明确、可回滚 | 不写卡，3 条验收口头确认 | 外部信号（编译/测试/日志） | 自己看 diff |
| **L1 常规** | 多文件、新功能、跨模块 | 任务卡（意图/边界/验收/回滚/停止条件） | C2 的 3–5 条 + 抽查验证器 | **两阶段**：先规格后质量 |
| **L2 变更** | 需求模糊、跨模块、要改规则 | 变更卡（Why / What / Impact / Spec 增量 / Tasks） | 同上 + 归档回规则 | 两阶段 + 归档检查 |
| **L3 缺陷** | 已发生的 bug | 缺陷卡（assess / fix / test） | 三态：`verified` / `partial` / `failed` | 只认 verified |

**原型例外**：隔离目录、标「不可上线」、不写卡；但不得直接进主干（B1）。

## 3. 从五家借来的具体措辞（可直接用）

- **两阶段审查**（Superpowers）：
  1. 这段改动满足的是**哪条验收**？逐条对上；对不上，先退回。
  2. 代码质量：异常路径、边界、命名、重复实现、依赖方向。
  顺序不能反——先质量后规格，会把"做错事"审成"做得漂亮"。
- **缺陷三态**（spec-kit）：`verified` 才算修好；`partial` 要写清缺哪条验证；`failed` 必须回到 assess，不许直接再改。
- **归档动作**（OpenSpec）：任务收尾多问一句——"这次改动更新了哪条规则/约定？"没有就写"无"。
- **verification gate**（Superpowers）：说"完成"之前，必须给出跑过的命令与输出；给不出就还是未完成。

## 4. 明确不合并的部分

| 不合并 | 理由 |
|---|---|
| spec-kit 九命令全流程 | 小任务过重；B8 要求 3 轮不收敛就动手 |
| OpenSpec Stores / 多 profile | 单人用不上；选项疲劳 |
| Superpowers 子代理并行 | 单人审查带宽固定（J5），并行只加深队列 |
| Superpowers 技能自动触发 | 15 个技能常驻 = 上下文税（M1） |
| Aider repo map | Qoder 已有检索与上下文管理 |
| GPT Engineer 整仓生成 | 仓库已归档；UAM 生产禁用 |

## 6. 许可与尺寸

- 借的是**机制与字段**，不是原文；模板为本项目改写，不复制第三方段落。第三方仓库仍按各自许可（MIT / Apache-2.0）留存于 `_extern/`，不并入本仓库的 CC BY-NC 范围。
- 尺寸：删除 tarball 与两个不再需要全文的仓库后，`_extern/` 控制在 40MB 以内；本仓库文档仍在 1–2MB 量级。

## 7. 判断标准（留一条给以后）

> 要不要引入一个新工具/流程，只问三件事：
> 1. 它补的是 L1–L4 的哪一层？本项目这一层是否真的缺？
> 2. 它带来的新动作，谁付人分钟？（M1）
> 3. 有没有更小的件能拿到 80% 的增益？
>
> 三条答不上来，就不引入。
