## 1. 十条核心判断（附推理链）

### 1.1 个体提效真实，组织净收益不确定 —— 这是全篇最重要的结论

**证据链**：DORA 2024（25% 采纳率 → 吞吐量 −1.5%、稳定性 −7.2%，A）→ DORA 2025（90% 采用、>80% 自报提效，但提出「mirror and a multiplier」，A）→ Stack Overflow 2025（84% 使用，但 66% 受困于「几乎对」的代码、45.2% 调试更耗时，A）→ GitClear（重构占比下降、重复与 churn 上升，B）→ 综合检索中的 Faros / LinearB 遥测（PR 评审时长与事故率上升，C）。

**判断**：AI 加速的是「生成」这一环，而交付是链路。只加速首环等于把队列变长，这就是「验证税」。因此手册把 C4（验证税计入估算）、B4（小批量）、D1（产出当待审 PR）都设为高优先级，而不是把精力放在「怎么让 AI 写得更快」。

**反例保护**：METR RCT 是边界条件而非普遍反例——它测的是「资深开发者 × 百万行自有代码库 × 难以贡献增量知识」。对新人、陌生代码库、新项目，方向可能相反；METR 自己列了四类「不提供证据支持」的外推，并于 2026-02 发布了后续数据表明方向会随工具演进而变化。手册 E2 因此写成「自报不作决策依据 + 注意选择效应」，而不是「AI 让人变慢」。

### 1.2 真正决定成败的是流程成熟度，不是模型分数

**证据链**：亚信科技对同一款工具的三团队效能评估（编码效率提升 1% vs >10%，需求交付 −1% vs +18.4%，B/C 级客户案例）→ DORA 七项能力模型（清晰的 AI 立场、AI 可访问的内部知识仓库、强版本控制、小批量、高质量内部平台等，A）→ DORA 2024 的「小批量 + 稳健测试」解释（A）→ Code Ninety 关于自动化准入与 TDD 消除大部分缺陷注入惩罚的说法（C，未回查）。

**判断**：工具不是决定变量。手册因此把 A/B/E 章（规则、拆解、度量）放在与 D 章（代码质量）同等甚至更高的位置。

### 1.3 「接口/约束设计」比「模型能力」更能撬动结果

**证据链**：SWE-agent 在模型不变的情况下，仅靠 Agent-Computer Interface 把 SWE-bench pass@1 从非交互式 RAG 的 3.8% 提到 12.5%（A）→ Agentless 反向删掉 agent loop，用固定三阶段 pipeline 达到 32.0% SWE-bench Lite 且成本约 $0.70/issue（A）→ 两者结论看似矛盾，实则共同指向「harness/流程设计显著影响结果」→ 12-Factor Agents 的「own your prompts / context / control flow」（A）→ `agents.md` 成为跨工具约定（A）。

**判断**：对用户最有杠杆的动作不是换模型，而是把仓库规则、任务工件、验收标准、反馈回路设计好。这是手册 A/B/C 三章的立论基础。

### 1.4 复杂 Agent 不是默认答案

**证据链**：Anthropic《Building Effective Agents》明确「先找最简单方案，只在必要时增加复杂度」，把 workflows（预定义控制流）与 agents（模型自决控制流）分开，并给出五种工作流模式（A）→ Agentless 证明固定 pipeline 可以胜过当时的开源 agent（A）→ SWE-agent 与 mini-swe-agent 的演化说明「控制循环会商品化，上下文管理仍是工程重点」（A）→ 12-Factor Agents 主张「大部分生产 agent 其实是确定性软件 + 关键节点的 LLM 调用」（A）。

**判断**：手册 B1 把模式选择做成风险档位表，B3 要求计划/执行分离，C3 要求循环有停止条件，都不鼓励「给个目标扔一堆工具让模型自己跑」。

### 1.5 反馈必须是外部、可观测的

**证据链**：Huang et al. ICLR 2024（无外部反馈的推理自纠不改善甚至变差，A）→ Reflexion（依赖环境反馈，A）→ Self-Refine（~20% 提升，但集中在风格/可读性等软标准，A）→ CRITIC（工具交互式批评，A）→ Zheng et al. 2023（LLM 判官与人类一致率 >80%，但存在位置、冗长、自我增强偏差，A）→ Vibe Coding 综述把反馈机制列为四大基础设施之一，细分为编译器/执行/人类/自我改进四类（A）。

**判断**：这条直接支撑 C1、C2、C3。特别地，「让 AI 自查一遍」在代码场景往往无效，除非手里有编译器、测试或日志。这与用户既有的「自检先请示」纪律方向一致但理由不同：前者是信息量问题，后者是权限与风险问题，手册把两者分别放在 C1 与 F5。

### 1.6 上下文是注意力预算，不是存储

**证据链**：Liu et al. TACL 2024 的 U 型位置曲线（A）→ 12-Factor Agents 的 dumb zone / compact errors / small focused agents（A）→ Anthropic「最小的高信号 token 集」（A）→ aider 只加入需编辑文件、repo map 只给符号骨架（A）。

**判断**：手册 B5 的推荐做法（重要信息置首尾、错误压缩、长任务拆短会话）有明确出处；同时提醒 `AGENTS.md` 也会挤占上下文，所以 A4 要求命令级、不写废话。

### 1.7 安全是独立维度，且不会随模型变强自动改善

**证据链**：Veracode 2025 测 100+ 模型，45% 样本引入 OWASP Top 10 问题、Java 72%、XSS 86%，且「模型越大越新，语法越好但安全性持平」（A）→ Perry CCS 2023（AI 组写出更不安全的代码，且更相信自己写得安全，A）→ Pearce S&P 2022（约 40% Copilot 生成程序含漏洞，A）→ Spracklen USENIX 2025（19.7% 推荐包不存在，A）。

**判断**：D4 必须设为 P0 且是门禁而非建议；D2（异常路径）、D5（幻觉依赖）是同一根因的不同表现。对有物理动作的项目，D2 的权重还要再提高。

### 1.8 「验收标准」是反馈机制的支点

**证据链**：Anthropic evaluator-optimizer 仅在「标准清晰且迭代有可测提升」时划算（A）→ Spec Kit 的 bug 流程要求 verified / partial / failed 三态（A）→ Zheng 2023 的判官偏差需要双顺序 + 可数指标抵消（A）→ METR 指出 benchmark 的成功定义（自动化测试）与真实任务（人满意、能过 review）不等价（A）。

**判断**：手册 C2 把「3–5 条可复核验收条目 + rationale」设为 P0，并在 4.3 给了任务卡模板。这也解释了为什么「你再检查一遍」几乎不产生价值——没有尺子。

### 1.9 企业披露的数据要按「口径」读，不能按「数字」读

**证据链**：腾讯 2024 口径「35% 代码由 AI 生成、采纳率 >28%」，2025 口径「50% 新增代码由 AI **辅助**生成」（B）→ 阿里「内部 AI 辅助代码生成比例接近 40%」（B，媒体转述）→ DORA 2024 与 2025 对吞吐量方向的结论发生反转（A）→ GitClear 不同版本报告对「重构占比」「复制粘贴占比」的年份与百分比不完全一致（B）。

**判断**：手册 E1 明确禁止把不同口径的百分比放进同一张比较表；7.2 规定引用数字必须同时写样本/口径/年份/是否相关性/可信等级。这一条本身也是本轮调研的工作方法。

### 1.10 助手偏好是「可覆盖的默认值」，不是外部事实

**判断**：F 章单独成节，明确标注「不是研究结论」，并允许一条用户指令覆盖。把「自检先请示」写进 P0 是因为它在用户环境中是真实约束，但要说明它与 C1 的理由不同，避免把个人纪律包装成行业最佳实践。

## 4. 四类来源各自的贡献边界

| 类别 | 回答了什么 | 回答不了什么 |
|---|---|---|
| 行业实践 | 大厂把 AI 投在哪些环节（腾讯同时投评审与测试）、组织怎么度量、架构怎么设计（Router-Worker） | 不能证明因果，不能作为自己团队的收益预期 |
| 开源经验 | 工具/约定支持什么、社区收敛到什么做法、怎么把流程工件化 | 不能证明「用了就一定更有效」 |
| 研究结论 | 有样本、有对照的证据与边界条件 | 样本外推受限；调查类多为相关性 |
| 助手默认偏好 | 输出怎么组织、什么动作要先请示 | 不是客观事实，可被覆盖 |

**交叉印证最好的三条**（多类来源指向同一结论）：
1. 小批量 + 快速反馈（DORA 研究 + aider git 工作流 + Spec Kit 工件化）。
2. 外部验证优于自评（Huang/Reflexion 论文 + Spec Kit 验证三态 + Anthropic evaluator 边界）。
3. 上下文需主动管理（Lost in the Middle 论文 + 12-Factor Agents + aider repo map + `AGENTS.md` 就近覆盖）。

## 5. 思考过程中被推翻的初始假设

1. **「查大厂实践主要是抄他们的提效数字」** → 推翻。数字口径混乱且多为自报，真正可迁移的是「分业务线归因」「AI 同时投评审与测试」「把人的注意力当瓶颈做架构」这三件事。
2. **「Agent 越自主越先进」** → 推翻。Agentless 与 Anthropic 都指向「固定流程 + 关键节点模型决策」更稳；手册因此把 UAM 明确排除在生产之外。
3. **「让 AI 多自查几轮能提高质量」** → 推翻。无外部信号的自评在推理类任务上无效甚至有害；改为「先写验收标准 + 外部信号 + 停止条件」。
4. **「把整个仓库喂进去更准」** → 推翻。U 型位置曲线与上下文预算都指向精简与首尾放置。
5. **「把项目-specific 的坑写进手册更有用」** → 部分推翻。用户明确要求「可以脱离项目上下文」，因此把具体内容抽象成编号准则，项目细节集中到第 5 章并标注可删除。

## 6.5 第二轮新增判断（v2）

### 6.5.1 最重要的收获是把三处过强的表述改弱了

1. **相关性 ≠ 因果**：DORA 2024 的 −1.5% / −7.2% 是横断面调查的建模关联，不是「采用 AI 后观测到的下降」，更没有干预实验。因此「小批量 + 稳健测试」只能写成 **DORA 提出的解释与建议**，不能写成「已被证明的止血机制」。合适表述是「预期有帮助，并会测量」。
2. **术语不冒认原创**：「验证税」在 DORA 2026-03 指引中已有 "verification tax" 提法（B/C 级转述，未回查原文）。手册沿用但标注出处与待回查状态。
3. **测试 ≠ 验收的充分条件**：TestGenEval（A）显示覆盖率 35.2% 对应变异分数仅 18.8%，最常见失败是「完全没有 assert」。ISSTA 2026 提示当被测代码本身已错时，变异分数与 bug 检测的相关性变弱 → **测试必须从验收标准生成，不能从实现生成**。

### 6.5.2 新增的四条立论

4. **评测整体 = 模型 + harness + 数据分区**：同一模型换 scaffold 可差约 10 点，Verified 与抗污染评测差可达 30+ 点，污染与测试缺陷会抬高分数，自报分数常无独立复现。→ G1/G2：不看单一榜单选工具，建私域回归集。
5. **加 Agent 的方向由任务结构决定**：Google 260 配置给出 −70%~+80.8%；顺序规划全线下跌；独立 Agent 误差放大 17.2× 而集中式 4.4×；Anthropic +90.2% 伴随 15× token 且 token 用量解释 80% 方差；CooperBench 两个 Agent 写共享文件成功率腰斩。→ B7：默认单 Agent，「writes stay single-threaded」。
6. **安全边界在「推理→动作」这一层，不在提示词**：MCP 官方明确工具注解不可信、调用前须明确同意、协议本身无法强制；OWASP 提出 least agency；DeepSeek 用纯函数 `gate()` 在模型之前做授权、observe 为默认模式。→ A3/H1/H2。
7. **成本会外溢，且外溢到看不见的地方**：AI slop 的公地悲剧把成本转给 reviewer capacity / codebase integrity / public knowledge / collaborative trust / talent pipeline；「指标是产量时，产出就是 slop」；curl 的案例里质量提升后负载并未下降。→ I1–I3、六维记分卡。

### 6.5.3 被强化的两条旧判断

8. **自报不作决策依据**：METR 2026-05 官方调查（349 人）给出「价值 1.4–2x vs 速度 3x」，并明确自报在 2025 年研究中平均高估 40 个百分点；建议改问价值、改问管理者。→ 新增「区分速度与价值」。
9. **METR 19% 的边界更清楚了**：2026-02 更新回访组 −18%（区间跨 0）、新招组 −4%，METR 自评 unreliable signal，30–50% 开发者隐瞒不愿无 AI 完成的任务造成向下偏误。结论不是「AI 让人变慢」，而是「该场景下效应未定、感知与实测持续背离」。

### 6.5.4 对自身输出偏好的再判断

v1 把 F 章写成「可覆盖的默认值」是对的，但没说**它与其他准则冲突时谁让路**。v2 补了 0.3 冲突消解（用户指令 > 安全 > 基线 > 验证证据 > 效率 > 助手偏好）。这条本身也是偏好——所以更该明写出来供用户覆盖，而不是藏在行为里。

## 7. 手册修订触发规则

- 出现新的高质量 RCT / 大样本纵向研究 → 优先复核 C4、E1、E2。
- 项目发生新的 P0 事故 → 更新 A1 规则文件骨架与 D2，并在本文件追加一条判断。
- 用户覆盖任一 F 章偏好 → 直接改 F 章并注明「用户覆盖」，不改其他章节。
