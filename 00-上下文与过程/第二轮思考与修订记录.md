# 第二轮思考与修订记录（v1.0 → v2.0）

> 日期：2026-11-11 12:02 起 ｜ 触发：用户要求「再次思考」，同样要求查阅思考不少于 10 分钟
> 本文记录 **v1.0 哪里不够、本轮补了什么、哪些结论被推翻或弱化**。不是资料摘录，资料在 `01/`–`03/` 与 `06-来源索引/`。

## 1. 对 v1.0 的自我批判

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 企业实践证据偏二手（DeepSeek 几乎全是媒体转述，腾讯数字来自百科汇编） | 三家公司的「工程实践」部分可信度不足，尤其 DeepSeek 被标为 C 级，等于没真正查到一手 |
| 2 | 引用了 SWE-bench 等分数，却没有讨论**评测方法论** | 把可能已被污染/被 scaffold 影响的分数当能力证据，是方法论错误 |
| 3 | 缺**协议与互操作层** | 没说 Agent 能触达什么、工具描述为何不可信、授权该在哪一层做 |
| 4 | 优先级没有压力测试 | P0 有 11 条，实际执行必然稀释；准则互相打架时无消解规则 |
| 5 | 缺**外部性与治理** | 只算团队内部账，没算对评审者、开源社区、公共知识、人才梯队的成本外溢 |
| 6 | 「验证税」被写成自己的归纳，且把 DORA 的建议写成因果结论 | 术语出处与证据强度都不严谨（**本轮最实质的修正**） |
| 7 | TDM（测试驱动）只说「人先写测试」，没说**测试本身可能无效** | 会让人以为「有测试 = 有验收」，实际上覆盖率与变异分数可以差一倍 |
| 8 | 多智能体只写了 orchestrator-workers 的正面，没写**什么时候不该并行** | 与 2025–2026 的实证结论脱节 |

## 3. 结论变更清单

### 3.1 被**弱化**（措辞强度下调，不是事实被推翻）

| 原结论 | 修正后 | 依据 |
|---|---|---|
| 「小批量 + 稳健测试是**多源验证的止血机制**」 | 改为「DORA 提出的**解释与建议**；DORA 数据是横断面调查的**建模相关性**，不证明任何特定控制（评审、治理、测试）能消除 AI 采纳带来的不稳定性。应表述为『我们预期这有帮助，并会去测量』」 | DORA 2024 官方 PDF/博客（A）；prompt-to-prototype 对证据性质的方法论梳理（B） |
| 「验证税」是本手册的归纳 | 该术语在 DORA 2026-03 的指引中已被明确提出（"verification tax"，生成阶段省下的时间被重新分配到 verification / prompting overhead）。**标注为行业已有提法（C 级转述，未回查原文），本手册沿用但不再声称原创** | re:cinq 对 DORA 2026-03 的引用（C） |
| 「AI 采纳率↑ → 吞吐量↓」 | 分年份陈述：DORA 2024 为 −1.5%，DORA 2025 官方称「正向反转」；共同且稳定的是**稳定性/验证承压** | DORA 2024/2025 官方（A） |

### 3.2 被**强化 / 精确化**

| 原结论 | 本轮补强 |
|---|---|
| METR 19% slowdown，并注明 2026-02 有后续数据方向变化 | 补到具体口径：late-2025 工具、57 名开发者 / 800+ 任务，回访 10 人 −18%（区间 −38%~+9%）、新招 47 人 −4%（−15%~+9%）；METR 自评 **"unreliable signal"**，30–50% 开发者隐瞒了不愿在无 AI 条件下做的任务 → 向下偏误；METR 因此重设计实验。官方 Frontier Risk Report（A）表述为「小而约 4–20% 的收益，幅度很不确定」 |
| 「自报不作决策依据」 | METR 2026-05 官方调查（349 名技术工作者）：**价值**中位 1.4–2x 而**速度**中位 3x；作者明确「速度会系统性高估价值」「2025 研究中人们平均高估 40 个百分点」「调查结果未必扎根于现实」；建议改问**价值**而非速度、改问**管理者/生产力研究者**而非个人贡献者。→ 新增准则「区分速度与价值」 |
| 「harness 设计比模型更影响结果」 | 补到量化：同一模型在不同 scaffold 下 SWE-bench Pro 分数可差约 10 个百分点；Verified 与 Pro 分数差可达 30+ 点，主要来自污染与难度；77 个 Verified 榜单条目当时无一独立复现（C/B 级来源，取**方法论结论**不取具体分数） |

### 3.3 全新补充（v1 完全没有）

| 主题 | 关键结论 | 落到的新准则 |
|---|---|---|
| **评测方法论** | SWE-bench Verified 存在训练数据污染与测试缺陷；测试补丁不完整使部分错误补丁通过；scaffold 方差大；自报分数缺独立复现；**覆盖率 ≠ 抓 bug 能力**（TestGenEval ICLR 2025：GPT-4o 35.2% coverage / 18.8% mutation score；最常见失败是「完全没有 assert」）；Meta 用「每个测试必须杀死一个 mutant」把接受率做到 73%；ISSTA 2026：mutation score 与真实 bug 检测 r=0.86，但**被测代码本身已错时相关弱 → 测试要从验收标准生成，不从实现生成** | G 章（G1–G4）、C2 修订、B1 TDM 修订 |
| **协议与最小权限** | MCP 官方规范：工具描述/注解**默认不可信**；Host 调用任何工具前须获**明确用户同意**；**协议本身无法在协议层强制这些原则**，由实现者负责。OWASP Agentic Top 10 2026（ASI01–ASI10）提出 **least agency**；五国联合《Careful adoption of agentic AI services》（2026-05）建议从小处着手、只用于低风险任务、从一开始就施加既有安全控制；NCSC「若无法理解/监控/限制 agent 行为，就没准备好部署」 | H 章（H1–H4）、A3 修订 |
| **多智能体的反面证据** | Google/DeepMind/MIT 260 配置研究：相对单 agent 从 **−70% 到 +80.8%**，方向由任务结构决定，不由 agent 数量决定；顺序规划任务上所有多智能体变体降 39–70%；独立 agent 误差放大 17.2x、集中式 4.4x。CooperBench：两个 coding agent 编辑共享文件，成功率约 50%→25%。Anthropic +90.2% 的多智能体研究伴随 token 15x，且 token 用量解释 80% 方差。Cognition 规则：**「writes stay single-threaded，额外 agent 贡献智能而非动作」** | B7（拆解的反面）、B3 修订 |
| **治理与外部性** | arXiv 2604.16754 把 AI slop 定位为公地悲剧：成本外溢到 reviewer capacity / codebase integrity / public knowledge / collaborative trust / talent pipeline；用 Ostrom 八原则给出：provenance 默认属性、AI 输出默认可审、指标改为下游成本、集体制定规则、分级制裁、争议与回归归属机制、教育中区分不可委托任务。「When the metric is volume, the output is slop」；「generation without review is extraction」 | I 章（I1–I4）、E1 修订 |
| **上下文经济** | Anthropic 官方 context engineering：context rot、attention budget（n² 注意力关系）、「最小高信号 token 集」、系统提示的正确海拔、最小工具集、just-in-time retrieval、compaction / 结构化笔记 / 子智能体；腾讯 SpecWorker 的阶段级上下文（P1 需求验收、P2 设计契约、P3 diff、P4 trace-id 日志、P6 delta spec 回灌），并指出 **SubAgent 不是免费的上下文隔离**（每个读全文件独立计费） | B5 修订、I4 |
| **DeepSeek 一手细节** | `dsh-superagent-prototype`（MIT，2025-10-31）源码级设计：**gate() 纯函数在模型之前做授权判定，模型无法绕过**；**observe 为默认模式**（只记录「本来会接受」，auto 需人显式开启）；Engine 唯一写入者 + transactional outbox；Router 提示词禁止看代码/读日志、路由说明 ≤30 词；聊天回复 ≤100 词；每条 GitHub 评论默认标注「automated agent, not a human」；16 个 worker 上限且额外留 1 slot 给人；**agent 以完整 OS 用户权限运行 → 必须隔离到独立用户/VM**；自测用假工具只消耗时间，**没测代码质量** | A3 修订（渐进授权的工程范例）、额外建议 2（provenance 标记已有实例） |

### 3.4 优先级体系的压力测试（新增）

v1 的 P0 共 11 条，实际执行会稀释。v2 新增：
- **冲突消解规则**（0.4）：用户显式指令 > 安全与不可逆 > 基线与可回滚 > 验证证据 > 效率与产出 > 助手默认偏好。
- **最小可行准则集**（4.5）：如果只能做 5 条，做哪 5 条。
- **成熟度阶梯**（4.6）：L0–L3 分级，避免一上来就上全套。
- **仓库健康记分卡**（4.7）：六维度、不折成单一分数、旁边并列交付价值。

## 5. 一句话总结本轮

v1 回答的是「和 AI 一起写代码该守什么规矩」；v2 补上的是「**这些规矩的证据有多硬、什么时候会互相打架、以及这套做法把成本转嫁给了谁**」。最有价值的不是新增了 12 条准则，而是把三处过强的表述改弱了。
