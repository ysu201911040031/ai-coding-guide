# 诊断

## Overview

**先复现，再改。** 每一次没有证据的修改，都在给系统增加变量，最后没人知道是哪个改动起了作用。

## When to Use

- 测试失败 / 构建失败 / 运行时报错
- 行为与预期不符、时好时坏
- 上一次修复没生效，或修好又坏

**不触发**：新功能开发（走 `project-kickoff`）、纯性能优化（先有基线再谈）。

## Process

1. **复现**：给出最小复现命令与完整输出。复现不了就先加日志 / 抓包 / 离线回放，**不许盲改**。
2. **定位**：二分变量——版本、提交、输入、配置、环境，一次只变一个。
3. **写假设**：一句可证伪的话——"原因是 X；如果是，改了之后 Y 会变绿，Z 不受影响"。
4. **最小修复**：只改与假设相关的行；不顺手重构、不顺手改格式。
5. **回归证明**：先写一个能复现该缺陷的测试（红），再修到绿；跑相关测试集。
6. **记录**：根因 / 证据 / 影响面 / 是否还有同类隐患（有就列出来，不在本次顺手改）。

## Rationalizations

| 借口 | 反驳 |
|---|---|
| "先改改看" | 盲改一次 = 多一个变量；两次之后你就不知道是谁修好的。 |
| "本地复现不了，直接去生产试" | 禁止。先拿日志、抓包、离线回放；生产只读观察。 |
| "修好了，测试就不加了" | 没回归测试 = 下次同错再来一遍。不可测就写明原因与替代证据。 |
| "顺手把这块也重构了" | 诊断阶段的改动只服务根因；重构另开任务。 |

## Red Flags

- 连续两次修改都说不清"为什么这样改"
- 同时改多个文件、多个配置
- 出现"应该是缓存问题""可能是并发"但没有证据
- 修复后没有新增/更新任何测试

## Verification

- 复现命令从红变绿，输出可贴
- 回归测试存在，且把缺陷重新引入后会变红
- 根因能用一句话讲清，且与证据链对得上
