# 任务卡 · 四车道

> 一页覆盖：小改 / 常规 / 变更 / 缺陷。**先选车道，再决定写不写卡**。
> 来源：机制改写自 spec-kit（bug 三态）、OpenSpec（change 归档）、Superpowers（两阶段审查、先红后绿）；文字为本项目重写。

## 0. 选车道

| 车道 | 触发 | 写什么 | 审查 |
|---|---|---|---|
| **L0 小改** | 单文件、需求明确、可回滚 | 不写卡；3 条验收口头确认 | 自己看 diff |
| **L1 常规** | 多文件、新功能、跨模块 | 任务卡 | 两阶段 |
| **L2 变更** | 需求模糊、跨模块、要改规则 | 变更卡 | 两阶段 + 归档 |
| **L3 缺陷** | 已发生的 bug | 缺陷卡 | 只认 verified |
| 原型 | 一次性、可丢弃 | 不写卡，隔离目录 | 标「不可上线」 |

## 1. 任务卡（L1）

```markdown
## 意图
做什么 / 为什么（一句话）

## 边界
允许改：<文件/目录>
禁止改：<文件/目录>

## 基线（实测）
路径：<abs> ｜ 分支：<branch> ｜ 未提交：<N>

## 验收（3–5 条，从需求写）
- [ ] <可复核条目> ｜ 怎么验：<命令/日志关键字/现象>
- [ ] ...

## 不做什么
- <明确不碰的东西，防顺手改>

## 回滚
<如何退回：git revert / 备份路径 / 开关>

## 停止条件
max_iterations：3 ｜ 连续失败 2 次转人工 ｜ 超范围立即停
```

## 2. 变更卡（L2，需求先对齐再写码）

```markdown
## Why
为什么要改；不改会怎样

## What Changes
- 新增：
- 修改：
- 删除：

## Impact
受影响模块 / 接口 / 数据 / 规则文件：

## Spec 增量（本次要沉淀的事实）
- ADDED：<新的约定/行为>
- MODIFIED：<改了哪条>
- REMOVED：<废掉哪条>

## Tasks
- [ ] 1. <任务> ｜ 验证：<命令/现象>
- [ ] 2. ...

## 归档（完成后填）
这次改动更新了哪条规则/约定？没有就写「无」。
```

## 3. 缺陷卡（L3）

```markdown
## Assess（先定位，不改代码）
- 复现步骤：
- 期望 / 实际：
- 根因假设（最多 3 条）+ 证据：
- 影响面：

## Fix（最小修复）
- 改了哪里 / 为什么这样改：
- 未修的部分与原因：

## Test（验证原症状）
- 复现用例（修复前必须失败）：
- 修复后结果：
- 回归项：

## 结论
状态：verified / partial / failed
- verified：原症状消失且回归通过
- partial：修了但缺哪条验证：___
- failed：回到 Assess，不许直接再改
```

## 4. 两阶段审查（L1 及以上，顺序不可反）

**第一遍：对规格**
- [ ] 每条验收都能指出对应改动
- [ ] 没有做验收之外的事（范围膨胀）
- [ ] 没有漏掉验收里的异常路径

**第二遍：对质量**
- [ ] 异常路径 / 前置条件 / 并发 / 超时
- [ ] 是否重复实现了已有 helper
- [ ] 依赖方向与分层未被突破
- [ ] 无硬编码凭据、无被注释掉的测试
- [ ] diff 可独立回滚，提交信息说清「改了什么、为什么、怎么验」

## 5. 完成前门禁（verification-before-completion）

说「完成」之前，必须贴出：

1. 跑过的命令
2. 关键输出（通过/失败）
3. 验收条目逐条勾选

给不出这三次，状态仍是「未完成」，不是「应该可以」。

## 6. 归档动作

- 一次性结论 → 当日日志
- 长期约束 → 规则文件（core / project.local）
- 可复用实现 → 共享代码地图（AGENTS 第 7 节）
- 以上都没有 → 写「无」，不要空着
