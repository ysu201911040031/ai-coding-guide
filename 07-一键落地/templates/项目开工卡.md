# 项目开工卡

> 对应准则：手册 **A6 项目骨架先定，再让 AI 动手**
> 用途：新项目启动、换仓库、接手陌生项目时，**在让 AI 写第一行代码之前**过一遍。
> 用法：复制本文件到新项目根，改名 `STATUS.md`，按 §0→§5 顺序填。**不填完不许开工**——顺序反了要返工。
> 判据统一是：**这一层谁会读、多久读一次**。答不出来的，不建。

---

## 0. 定位四问（比建目录更早，先答完这个）

> **为什么排在最前**：下面每一节都靠这四问定位。项目在哪，决定三个入口文件放哪；git 在哪，决定「能不能回滚」（A3 所有审批的前提）；资料在哪，决定记忆与资料谁是谁；有哪些 skill，决定 AI 手里已经有什么工具、哪些会绕过审批。
> **四问全部要写绝对路径或明确答复，不许写「默认」「一般」**。写不出来的当场问人，别猜——这属于「运行期事实」，静态读代码推不出来。

### 0.1 项目在哪

```
项目根（绝对路径）：
当前是什么：□ 空目录新建  □ 已有代码接手  □ 从别的仓库拆出来
```

**判据**：这个路径**本身就是**你以后所有相对路径的锚。如果它在一个更大的目录里，问清楚「那个更大的目录是不是也要一起管」。

**踩过**：接手别人的项目时，人常把「仓库根」和「代码所在的那层」混着说。差一层，`AGENTS.md` 就放错地方，AI 读不到。

### 0.2 git 在哪

```
git 仓库根：            ← 跑 git rev-parse --show-toplevel 得到的，不是猜的
当前分支：
有无未提交改动：□ 无  □ 有，共 ___ 个文件
有无远程：□ 有，地址 ___   □ 无（只有本地，机器坏了就没了）
有无嵌套仓库：□ 无  □ 有，路径 ___（这些目录不得入库）
是否有多个 worktree：□ 无  □ 有，路径 ___
```

**四种真实形态，必须分清**：

| 形态 | 怎么认 | 后果 |
|---|---|---|
| 项目自己就是 git 根 | `show-toplevel` == 项目根 | 正常 |
| 项目在父仓库的子目录里 | `show-toplevel` 是**父级** | 提交会提交到父仓库；回滚会回滚别人；`.gitignore` 要写在父级 |
| 内部有嵌套 `.git` | `find . -name .git -not -path "./.git"` 有结果 | **外层 `git add .` 会把嵌套目录变成 gitlink**，`diff` 从此失效 |
| 根本不是仓库 | `show-toplevel` 报错 | **无回滚能力**，A3 的审批失去意义 → 先 `git init` |

**判据**：**「我改坏了，一条命令能不能回到今天早上？」** 答不上来就别让 AI 动手。

> 本仓库实测踩中第三种：`ai-coding-guide/.git` 是独立 GitHub 仓库，嵌在母本里。不排除的话，`git add .` 会把它变成一个指针，外层再也看不到它的内容变化。

### 0.3 资料放在哪

**先跟 §3 的记忆分清**，两者最容易混：

| | 记忆 | 资料 |
|---|---|---|
| 判据 | **这段内容改了，代码要不要跟着改？** | **这个文件会被别的项目再打开吗？** |
| 要跟代码改 | ✅ 记忆 | ❌ |
| 跨项目复用 | ❌ | ✅ 资料 |
| 例子 | 行尾策略、构建命令、踩过的坑 | 参考资料、调研笔记、可复用模板、历史归档 |
| 放哪 | 跟项目仓库走（或镜像同步，见 §3.1） | 集中一处，**不进项目仓库** |

```
资料库根（绝对路径）：
本项目在资料库里的位置：        ← 没有就写「无，本项目不需要」
```

**踩过**：把调研笔记塞进项目仓库，三个月后仓库 60% 体积是没人再看的 PDF。反过来把「不许改 `dist/`」写进资料库，AI 每次会话都读不到。

### 0.4 本地 skill 有哪些

> 这一问的作用不是「炫技」，是**划出 AI 手里已有的工具边界**——尤其哪些 skill 会执行命令或对外发消息，它们会绕过「自检先请示」。

**怎么查（三步，别凭印象）**：

```bash
# 1 看本机实际装了什么（用户级）
ls ~/.workbuddy/skills/ 2>/dev/null
# 2 看项目级
ls .workbuddy/skills/ 2>/dev/null
# 3 看台账里登记过的（含内置）
#    <资料库>/10-资源台账/skill台账.md
```

```
已装且本次要用：        ← 写名字 + 它干什么
已装但本次禁用：        ← 写名字 + 为什么禁用
R2/R3 类（会执行 / 会外发，用前必须问）：
```

**风险四档**（沿用 `10-资源台账/skill台账.md`）：

| 档 | 能力 | 处理 |
|---|---|---|
| R0 只读 | 读文件、检索、分析 | 直接用 |
| R1 本地写 | 生成/改本地文件 | 直接用，产出要验收 |
| R2 执行 | 跑命令、编译、调外部程序 | **先请示** |
| R3 外发/凭据 | 联网写、发消息、访问账号 | **人工批 + 凭据不落盘** |

**判据**：**凡 R2/R3，必须在 `AGENTS.md` 里点名写出「用前先问」**。没写＝AI 会用默认行为，而默认行为通常是「直接干」。

> ⚠ **AI 自报的 skill 清单不可靠**：它只能看到本会话注入的那部分，看不到你装了但未启用的。**这一问必须由人确认或查目录**，不能让 AI 自己填。

## 1. 三个入口（先决定读者，再决定内容）

| 文件 | 读者 | 多久读一次 | 写什么 | 不写什么 |
|---|---|---|---|---|
| `README.md` | 人（第一次来，或三个月后的自己） | 极少 | 这是什么、怎么跑起来、目录在哪 | 命令级约束（那是 AGENTS 的活） |
| `AGENTS.md` | AI（每次会话） | 每次 | 命令、硬约束、禁用写法、已知坑、运行期真相 | 人类背景故事、营销式介绍 |
| `STATUS.md` | 自己（每次开工 / 收尾） | 每天 | 做到哪 / 下一步 / 坑 / 别碰 / 验收 | 需求文档、设计长文 |

> `STATUS.md` 的五行格式与 `个人手册-提炼版.md` §7 同源，直接抄：

```
## 交接 YYYY-MM-DD
做到哪：___
下一步：___
坑：___
别碰：___
验收：___
```

**检验**：三个文件各自的第一段，能不能用一句话说出「谁会在什么场景下打开它」？说不出就是有一个多余。

## 2. 目录结构（按读者分层）

先回答下表，再建目录。**答不出「谁读」的一律不建。**

| 目录 | 谁读 | 什么时候读 | 不建会怎样 |
|---|---|---|---|
| `src/` | 编译器 / 人改代码时 | 每次构建 | 无法构建 |
| `tests/` | CI / 人查回归时 | 每次提交 | 不知道改坏没有 |
| `docs/ai/` | AI 按需加载 | 遇到特定主题时 | AI 每次重新猜约定 |
| `<填>` | `<填>` | `<填>` | `<填，写不出就删掉这行>` |

**硬规则**

- `docs/ai/` **只放索引 + 3–5 篇专题**，每篇不超过一屏。放大段规范等于让 AI 每次都读完它。
- 索引长这样，让 AI 自己按需加载，而不是让它通读：

```markdown
# AI 参考资料索引
- 改数据库结构时读：docs/ai/数据库约定.md
- 涉及定时任务时读：docs/ai/调度与幂等.md
- 报错信息含义不明时读：docs/ai/错误码表.md
```

- 不建 `01-需求/02-设计/03-测试/04-上线` 这类**按阶段编号的空目录**。它们看起来专业，三个月后会塞满过期内容，且没人负责清理。

## 3. 项目记忆（两份，永不合并）

> **与 §0.3 资料的分界**：记忆是「改了代码就得跟着改」的东西，资料是「跨项目复用、不跟代码变」的东西。判断不清时用这一句问：**这个月改了代码，这段内容要不要一起改？** 要 → 记忆；不要 → 资料。
> 混在一起的后果是双向的：记忆塞进资料库 → 三个月后说的和代码做的不是一回事；资料塞进记忆 → 每次会话都在读没人再看的旧文档。

### 3.1 先指定唯一真相源

| 选项 | 适合 | 代价 |
|---|---|---|
| 跟项目仓库走（`<项目>/.ai/memory/`） | 代码类项目，记忆要随代码演进 | 分散在多仓，不易总览 |
| 集中在资料库（`<资料库>/05-项目落地/<项目>/`） | 多项目统一管理，便于横向对照 | **与代码分离，容易与实现脱节** |

**选定一个写在这里，不要两处都改**：

```
真相源：<填路径>
镜像：  <工具自动加载的目录，如 <工具配置目录>/projects/<工作区标识>/memory/>
同步命令：cp "<真相源>"/*.md "<镜像>/"
```

> ⚠ 选「集中在资料库」的，必须额外守一条：**每次改完代码，先改真相源，再同步**。否则三个月后记忆说的和代码做的是两件事。
> 这条代价是真实的——`<项目名>` 项目已经出现过「项目约定实例」与「项目规则」两处各写一遍同一批事实（主仓路径、`禁止手改`、`BUILD_VER`、`content_hash`、`appid`），而逐行 diff 只查出 5% 重复。

### 3.2 两份文件各写什么

| 文件 | 放什么 | 判据 | 上限 |
|---|---|---|---|
| `MEMORY.md` | 环境事实、踩过的坑、不可违背的约束、行尾/编码策略 | **一个月后还会查** | 3000 字符，超了蒸馏进档案 |
| `YYYY-MM-DD.md` | 当天做了什么、为什么这么选、否决了什么 | 只追加，不回头改 | 无 |

**写 MEMORY 的典型条目**（都是「读代码读不出来、且会重复踩」的）：
- 本机/目标环境锁定值（框架版本、编译器等）
- 不能改的配置项（改了会让校验机制失效的那种）
- 生成物目录（`dist/`、`build/`、`web/` 之类，禁止手改）
- 一条踩过的坑：现象 + 真因 + 正确做法

**不要写进 MEMORY**：能 `grep` 出来的函数名、能从代码看出的架构、一次性的调试过程。

### 3.3 模块记忆：第 3 周再切，别在开工时切

> **默认不切。** `MEMORY.md` 一份够用，直到下面三个信号全部出现。

**开工就切模块记忆是错的**，因为那时模块边界只是猜的（领域边界在写代码前不存在）。第 8 天你会发现某个功能横跨原定两个模块，或某个"模块"三周没人碰。此时按当时的划分建目录，等于**把错误固化进结构**——改结构比改内容贵得多。

**三个信号都达到才切**（缺一个都再等）：

- [ ] 连续两周没有新增顶层目录
- [ ] 每个模块至少被改过 2 次
- [ ] 跨模块改动占比 < 30%（算法见下）

**怎么量跨模块改动占比**（每周跑一次，只读）：

```bash
# 近 7 天「碰了 ≥2 个顶层目录」的提交占比
git log --since='7 days ago' --format='C %H' --name-only \
  | awk '/^C /{if(n>1)cross++; tot++; n=0; delete seen; next} \
         NF && $0 ~ /\//{split($0,a,"/"); if(!seen[a[1]]++)n++} \
         END{printf "跨模块 %d/%d = %.0f%%\n",cross,tot,cross*100/tot}'
```

> ⚠️ **`delete seen` 不能漏**。少了它，`seen` 会跨提交累积，越往后的提交越难被算成"跨模块"，
> 结果系统性偏低。实测同一仓库：**有 `delete` = 44%，没有 = 11%**，差四倍。
> 这个坑值得记住——**统计脚本本身出错时，结论会"看起来合理"**，比报错更危险。

> 一半以上提交都碰两个以上模块 → **别按模块切**，改用「按动作切」（见下）。
> 实测参考：本仓库手册 14 章的跨章引用占 **86%**（105/122 边），只有 3 章能独立读。文档章节比代码模块耦合高，但这说明**"章节独立"是个错觉**，代码模块请用自己的数字判断，不要套用。

### 切了之后：三个文件 + 一条退路

```
.ai/memory/            （或 <资料库>/05-项目落地/<项目>/）
├── MEMORY.md          ← 保留，放跨模块的不可违背项
├── INDEX.md           ← 模块 → 触发条件，≤50 行
├── COUPLING.md        ← 耦合台账，≤70 行
└── modules/<模块>.md  ← 首行必写「读我当：…」
```

**模块记忆模板**（四节固定，第四节最有用）：

```md
# <模块名>
读我当：改 X 的 Y / 遇到 Z 报错 / 动 <文件名>

## 不变量（动了会坏什么）
## 踩过的坑（日期 + 现象 + 一句为什么）
## 依赖谁、被谁依赖（写模块名，不写文件路径）
## 这个模块不该知道的事
```

**`INDEX.md` 只写两列**，不要写目录树：

| 模块 | 读我当 |
|---|---|
| `<名>` | 改 `<文件名>` / 报错 `<关键字>` |

> 索引的是「**触发条件**」不是「结构」。结构会过期，触发条件不会。

**`COUPLING.md` 只记一件事：哪些东西被几处共用。**

```md
| 共用的事实 | 出现在 | 改它要同步 |
|---|---|---|
| 打包排除表 | build-clean-dist.py / check-drift.py / 映射表.md | 3 处 |
```

> 这是「关联索引」的真正落点。**模块切分的致命伤是跨模块约束，它不属于任何模块**。
> 本仓库实例：一条排除规则同时被打包脚本和对账脚本使用，改一处必坏另一处（D-12）。

**三条硬上限（超了必须动，不是建议）**：

| 文件 | 上限 | 超了怎么办 |
|---|---|---|
| `INDEX.md` | 50 行 | 模块切太细，合并 |
| 单个 `modules/*.md` | 80 行 | 只留「不变量 + 坑」，过程全丢 |
| `COUPLING.md` | 70 行 | **耦合太重，退回按动作切** |

**退路：按动作切**

`COUPLING.md` 涨到 50 行，说明「模块够独立」这个前提不成立。此时改用**动作**作切分轴——触发读取的从来不是代码模块，是你要做的动作：

| 轴 | 切分依据 | 耦合 | 风险 |
|---|---|---|---|
| 按模块 | 代码在哪 | **藏起来**（在别的模块记忆里） | 漏读不报错 |
| 按动作 | 要做什么 | **外显**（触发条件可查） | 索引本身会过期 |

动作型条目这样写：`改排除规则 → 读 build / drift / 映射表 三处`。它会横跨三个代码模块，但**这正是事实**。

## 4. 对话留痕（默认不留全文）

| 情形 | 怎么做 |
|---|---|
| 常规任务 | 不单独留档。决策一行写进 `STATUS.md` 的「为什么」 |
| 有过返工、换过方案 | `decisions/YYYY-MM-DD-<主题>.md`，写「候选方案 / 否决理由 / 最终选择」 |
| 多人协作、需要交接 | 同上，另在 `STATUS.md` 指向它 |

**会话原文（`.jsonl`、导出的 md）一律放仓库外。** 理由：会让 `git log` 变噪音，体积大，且可能夹带凭据。

## 5. 开工前最后五问

1. **§0 四问都写完了吗？** 项目根、git 根、资料库根、R2/R3 skill 清单——**四个都是绝对路径或明确答复**，没有「默认」「一般」。
2. 三个入口文件都建了吗？`STATUS.md` 里的「下一步」写的是不是**今天真能做完的一件事**？
3. 记忆真相源指定了吗？镜像同步命令能跑通吗？
4. 新目录如果现在就要建一个，你能说出「谁在什么时候读它」吗？说不出就别建。
5. **现在要不要建模块记忆？** 默认**不建**（§3.3）。除非三个信号都已达到——否则就是在猜边界，而错边界会固化成结构。

> 五问都过了再让 AI 动手。这不是流程洁癖——A6 的核心就是：**骨架定错的成本，会在后面每一条准则上重复收一次。**
>
> 第 1 问单独拎出来的原因：**前三个问题问错，后面全部白填**。项目根错一层，三个入口就放错地方；git 根错，回滚不了却没人事先知道；资料与记忆混，三个月后两边打架；skill 清单漏了 R3，AI 会绕过审批直接发出去。

## 附一：最小集（只有 3 分钟时）

1. **跑三条命令**，把答案抄进 `STATUS.md` 第一段（这是唯一不能省的一步）：
```bash
git rev-parse --show-toplevel   # git 在哪
pwd -W                          # 项目在哪（-W 给 Windows 形态，才能跟上一行比）
find . -name .git -not -path "./.git" -maxdepth 3   # 有没有嵌套仓库
```

> ⚠ **路径格式会打架**（实测）：Git Bash 下 `pwd` 给**小写盘符 + 正斜杠**形式（`/<盘符小写>/<路径>`），`git rev-parse` 给**大写盘符 + 冒号**形式（`<盘符大写>:/<路径>`）。**填表统一用后者**，因为它跨工具通用；斜杠开头的形式只在这一种 shell 里有效。
> 要比对「项目根 == git 根」时，用 **`pwd -W`**（Windows 形态）而不是 `pwd`——实测 `pwd -W` 与 `git rev-parse --show-toplevel` 输出完全一致，可以直接字符串比。
2. 建 `AGENTS.md` + `STATUS.md`（后者只写五行）。
3. 指定一处记忆真相源，其余标为镜像。
4. 在 `AGENTS.md` 写一行：「新目录必须能回答『谁在什么时候读它』，回答不出就不建。」

其余部分等真的需要改结构时再回来读。

> 资料库位置与 skill 清单**默认不写**：前者只在「这个文件会被别的项目再打开」时才需要，后者只要在 `AGENTS.md` 里点一句「R2/R3 类 skill 用前先问」即可。**这属于「答不出就不建」的同一判据。**

## 附二：§0 四问填完后，抄进 `AGENTS.md` 的版本

四问的完整版是给**人**看的一次性表单；`AGENTS.md` 里只留 AI 每次会话真需要的那几行，**不要整段复制**（理由是 A1 上下文预算 + ETH Zurich 实测：仓库概览和目录说明对任务成功率无效，详见 `02-开源经验/开工准备-GitHub提案横向对照.md` §4）。

```markdown
## 环境事实（运行期，读代码读不出来）
- 项目根：<绝对路径>
- git 根：<绝对路径>（分支 <name>，远程 <有/无>）
- ⚠ 嵌套仓库：<路径>，**不得 `git add` 该目录**
- 目标环境：<框架/版本/OS/编译器>

## 工具边界
- R2 类（会执行命令）：<skill 名> —— **用前先问**
- R3 类（会外发/用凭据）：<skill 名> —— **用前先问 + 凭据不落盘**
```

> **只写这四类**：路径、git 形状、环境锁定值、skill 边界。**不写目录树、不写架构概述、不写「本项目使用 XX 框架」**——那些 AI 自己 `ls` 一遍就知道了，写进去只花 token 不改变行为。
