## 1. 与前两家的根本差异

腾讯是工具/平台厂商，阿里是「模型—工具—云生态」厂商；**DeepSeek 既不披露全公司研发效能 KPI，也不是 AI 编程工具厂商**。它的公开材料集中在两块：

1. **内部「自用模型」评测**：模型到底能不能干真实研发任务（不是「用了之后效能提升多少」）。
2. **Harness / Agent 架构设计**：怎么组织多个会话与人的注意力。

这个差异本身是一条重要判断：**「模型能力」与「组织效能」是两类证据，不能互相代替**。手册把它写进了 E2 与 1.1。

## 2. 内部 Code Agent 评测（技术报告第 5.4.4 节，C 级 / 待回查）

- 样本：从 50+ 名工程师收集约 200 项真实研发任务（功能开发、bug 修复、重构、诊断），技术栈含 PyTorch、CUDA、Rust、C++；严格筛选后保留 **30 项**作为评测集。
- 结果（媒体转述口径）：V4-Pro-Max 通过率 67%，对比 Sonnet 4.5 47%、Opus 4.5 70%、Opus 4.5 Thinking 73%、Opus 4.6 Thinking 80%、Haiku 4.5 13%。
- 内部调研 N=85：全部受访者日常用 V4-Pro 做 agentic coding；52% 认为可作默认主编程模型，39% 倾向同意，<9% 反对。
- 主要负面反馈：**低级错误、对模糊 prompt 的误解、偶发过度思考**。
- 官方定位（转述）：整体发展轨迹约落后最前沿闭源模型 3–6 个月。

**可迁移的判断**（与具体分数无关）：
- 用**自己团队的真实任务集**评测模型，而不是只看公开 benchmark。对应手册 E2 与 6.2 的「回归任务集」额外建议。
- 「模糊 prompt 误解」是高频失败模式 → 对应 B2（工件化）、C2（验收标准先写死）、A4（命令级规则）。

## 3. 执行反馈强化学习（RLEF，C 级 / 待回查）

训练路线上据称用**执行反馈**惩罚：冗余工具调用、未处理 bash 错误码、浪费的多轮 diff 回滚。基准变化（终端/整任务类）：Terminal-Bench 4.0 31.2 → 42.3；ProgramBench 20.3 → 29.1；DeepSWE v1.1 单次通过率 74.2% → 77.0%。单任务平均费用约 3.3 元 → 1.3 元。

**可迁移的判断**（不依赖分数真实性）：把「工具调用是否经济、错误码是否处理、diff 是否反复回滚」当作可优化信号，与手册 C5（错误压缩）、B4（小批量）、C3（停止条件）同构。**反馈信号必须来自执行环境**，这与 C1 的研究结论一致。

## 4. Router-Worker / Super-Agent 架构（最有独特价值的部分，C 级 / 待回查）

**核心论点（工程判断，值得单独记住）**：
> 真正的瓶颈不是单任务模型能力，而是**一个人能同时盯住几个会话**——普通人只能跟住 3–5 个活跃会话（supervision bottleneck）。因此架构要「占最少的人的注意力，给最大的价值」。

**架构**：
- **Router**：长驻会话，订阅 GitHub / 群聊事件，判定授权并开 Ticket；限制工具集，负责所有交互与分派。
- **Worker**：每个 Ticket 一个隔离会话、独立目录，长任务设后台超时保持响应；结果回 Engine，再路由回原会话（通常是 PR）。
- **状态与计算分离**：授权状态、工单进展、交互历史写入本地轻量库；执行环境容器化；外部看门狗可从中断点恢复。
- **通信纪律**：确认一次，执行期间保持安静，只在「有结果 / 有问题 / 有失败」时再说话。
- **主动触发**：不等 prompt，监听报障消息，自行复现、修复、提 PR。

**自报仿真数据（仅存档，不引用）**：约 300 条消息中含 20 项真实请求；p50 完成 12.4 分钟，p95 15.7 分钟 vs 单会话基线 29.5 分钟；~40 请求/分钟时 Router 批大小 2.8、延迟 3.9 秒。消融：去掉事件直通后 Router 决策数 +约 30%、缓存读 token +约 37%。

**三点必须注明的限制**：① 全部为自报的内部仿真；② 测的是**任务调度与完成耗时**，不是真实任务的编码质量；③ 开源版本（MIT）明确说明与内部版本不同、部分设计仍是未来方向、工程风格不一致（相当部分代码本身由编程智能体写成）。

## 5. 对本手册的贡献

| 架构思想 | 对应准则 |
|---|---|
| 人的注意力是稀缺资源 → 会话数要克制、通信要节制 | B5（上下文/会话管理）、F1（输出结构，减少噪声） |
| Router / Worker 分离 = 控制流与执行分离 | B3（计划与执行分离）、12-Factor Agents「own your control flow」 |
| 状态外置、可从中断点恢复 | A2（基线确认）、A5、4.1 规则文件「可回滚性」 |
| 只在「结果/问题/失败」时汇报 | F1（先结论后展开）、C3（停止条件） |
| 授权判定前置 | A3（不可自动执行清单） |
| 用真实任务集自评 | E2、额外建议 1（回归任务集） |

## 6. 明确不采纳

- 任何具体通过率、基准分数、费用数字、p95 加速比（未回查 + 自报仿真 + 模型命名与官方口径可能不一致）。
- 网上流传的模型横向对比表（媒体制作，版本命名与官方口径不一致）。
- 「主动监听群聊自动提 PR」直接照搬到生产仓库——它跳过了 A2 基线确认与 A3 审批，属于典型 UAM 风险。
