## 1 五个我们没有的观点（按价值排序）

### 1.1 护栏而非手册 + 「犯错即加一条」的飞轮

- 原文：*「你的 CLAUDE.md 应该从小开始，基于 Claude 做错的事情来记录。不要试图预先写一本完整手册，而是每次 Claude 犯错，就加一条规则。」*（引 Shrivu Shankar）
- 硬数字：**Boris（Claude Code 创建者）团队的 CLAUDE.md 约 2500 tokens、约 100 行**。
- 飞轮：犯错 → 记录 → 下次不再犯 → 错误率下降。Boris 甚至在 PR 上 `@.claude` 让它自己把规则写进去，并说 *「Claude 非常擅长为自己编写规则」*。

**为什么比我们强**：我们的手册是「预先穷举」，它是「事后增量」。我们写了 62 条准则，只有极少数是被真实错误逼出来的；它的每一条都对应一次踩坑，天然精简、天然有效。
**落点**：`07-一键落地/rules/` 两份文件应改为「只增不改的踩坑台账」式维护——**新规则只能来自一次真实错误**。

### 1.2 收录判据：Claude 能从代码读出来的，不要写

| 该写 | 不该写 |
|---|---|
| 猜不到的 Bash 命令（自定义构建脚本） | 「这是一个 React 项目」 |
| 与默认不同的风格偏好 | 标准语言规范 |
| 测试命令与框架偏好 | 详细 API 文档（给链接） |
| 架构决策与背景 | 频繁变化的信息 |
| 环境坑（特殊变量） | 文件逐一描述 |
| 常见陷阱与修复 | 「写整洁代码」「遵循最佳实践」 |

**为什么比我们强**：我们只说「写约束不写规范」，没给**可判定的收录测试**。这条一句话就能判断该不该写。

### 1.3 三层模型：Prompt / Context / Harness，回报性质不同

| 层 | 是什么 | 投入方式 | 回报 |
|---|---|---|---|
| Prompt | 你说的话 | 每次都要重新投入 | 一次性 |
| Context | AI 能看到的信息（规则文件、结构、历史） | 写一次，持续生效 | 复利 |
| Harness | Skills / Hooks / MCP / 并行编排 | 搭一次，永久运行 | 指数 |

原文：*「如果只记住一件事，就记住这个：把时间花在构建 Context 和 Harness 上，而不是优化 Prompt。」*

**为什么重要**：这正是我上一轮说的「文档 → 机器」的另一种表述，且给了更好的命名。我们停在 Context 层（规则文件已是 Context），**Harness 层几乎为零**——没有 hook、没有 CI 门禁、没有自动化验收。

### 1.4 只写「永远不要做 X」会把它卡死，必须给替代

> *「当 Claude 觉得必须做 X 时它会卡住。永远提供替代方案：不要用 `--foo-bar`，改用 `--baz`。」*

**为什么比我们强**：我们的规则里有大量「禁止」「不得」「不准」，没写替代路径。缺替代的禁令在真实场景里会被绕过或卡住。

### 1.5 上下文压缩有损，且损失会累积

- 触发条件：长对话（约 40 分钟～1 小时）触发 compaction，**有损**；多次压缩后最早的约束只剩影子。
- 由此得出可执行阈值：**任何对 AI 说过两次以上的要求，就写进规则文件。**
- 同源现象：Claude Code 后台有子代理定期修剪记忆，目标是 **约 200 行**。

**为什么重要**：我们缺一个「何时把口头要求升级成规则」的触发器。这条给了：**两次**。

## 2 与我们的准则冲突的三处（用 K 章六步裁决法）

### 冲突 1：多 Agent 并行 ↔ 我们的 B7「默认单 Agent」

| 项 | 书 | 我们 |
|---|---|---|
| 主张 | 开 5–10 个 session 是「第一条生产力建议」，等待时间降到零 | 加第二个 agent 前，先用自有 eval 证明它赢过单 Agent |
| 因变量 | **墙钟时间 / 吞吐** | **净收益 / 缺陷率 / 人的审查容量** |
| 作者自己给的反证 | 6 个 agent 写 10 章：token 6×、一下午 $50、**风格不一致需统一审校**、多 session 同分支「冲突解到怀疑人生」 | — |

**裁决**：两者不矛盾，是**因变量不同**。并行提高的是产出速率；当审查容量是瓶颈时，它只是把队列变长（J5 不等式：`Δ生成 > Δ验证 + Δ返工` 才划算）。
**适用条件**（把书的经验变成判据）：① 任务可独立切分；② 合并成本低（不共享文件/状态）；③ **你有余量审**。三条缺一，并行就是负债。作者自己也说「从 2 个开始」——这已经接近我们的立场。

### 冲突 2：「执行层面可以完全信任它」↔ 我们的「外部信号验收」

书原话：*「Claude Code 是工程师，不是产品经理。执行层面可以完全信任它，但方向性决策必须你自己来。」*

**裁决**：这句话的成立范围由**爆炸半径**决定，不由「执行/决策」决定。
作者的域是前端页面、内容、iOS 小产品——错了一分钟能回滚；换成设备控制、不可逆物理动作、通信时序这类域——错一次不可逆。
**修正表述**：信任半径随爆炸半径收缩。可回滚的域可以「完全信任」；不可回滚的域，连执行层也要验。

### 冲突 3：「别花太多时间研究工具，去构建东西」↔ 这套 6000 行的档案

书最后一句：*「我的建议就一条：别花太多时间研究工具，去构建东西。」*

**这条是对我们这套东西最直接的批评，而且成立。**
判别方式（我们自己的 L 章）：**如果它没有改变过任何一次实际决策，它就是自我沉溺。** 上一轮定的「速查卡 0 次打开就归档」正是同一判据，只是我当时没想到作者会用一句话把它说得更狠。

## 4 可直接采纳的三处改动

1. **规则文件加「替代方案」列**：每条「禁止 X」后面必须跟「改用 Y」。现有两份规则里约有 12 条纯禁令，补替代。
2. **收录判据写进规则文件头部**：一句话——*AI 能从代码读出来的不写；猜不到的、踩过坑的才写。*
3. **加一条升级触发器**：*同一个要求说过两次 → 当天写进规则文件*（对抗压缩有损）。

暂不采纳：并行 session、Agent Teams、`/batch`。理由见冲突 1——判定条件（有余量审）当前不成立。
