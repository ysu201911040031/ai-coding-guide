# 05-项目落地 · 按项目分子目录

> 这一章是**示例实例**，与通用部分无关，可整章删。
> 通用骨架留在本目录根上；**每个具体项目一个子目录**。

## 约定

- 根上只放**通用**工件：`AGENTS.md骨架草案.md`（任何项目都能照着填）。
- 每个项目一个子目录，**目录名＝项目名**（如 `<项目名>/`）。
- **子目录不随通用包分发**：打包时整块排除，别人拿到的包里只有根上的通用骨架。
- 子目录里放该项目的四件套：落地对照清单 / `project.local.md` 填好的样子 / 项目硬约束全文 / `AGENTS.md` 成品。
- 加新项目＝**加一个子目录**，不要把文件平铺在根上——平铺会让「哪些是通用、哪些属某项目」立刻糊掉。

## 现有子目录

| 子目录 | 内容 | 文件数 |
|---|---|---|
| `<项目名>/` | 手册准则 → 该项目条目的映射、`project.local.md` 实例、项目规则全文、`AGENTS.md` 成品 | 4 |

> 本表**只写形态不写真名**：本文件是通用说明，会随包分发。
> 本机实际有哪些项目子目录，直接看目录列表，或记在本机私有笔记里。

## 与通用部分的边界

- 本目录里的**项目名、构建命令、硬件铁律、版本约束一律不外溢**到主手册、速查卡、`07-一键落地/` 配置包。
- 反向也成立：**通用空间不引用任何项目子目录**。这样把通用部分单独拷走时不会拖出一堆断链。
- 换项目时：复制骨架草案 → 在新子目录里填 → 用 `07-一键落地/setup.sh --proj=<仓库>` 安装。

## 为什么要有这一层（一条踩过的教训）

项目实例文件一开始是**平铺在根上**的，和通用骨架混在一起。后果不是难看，而是**分不清哪个能分发**：
打包时得逐个文件判断「这份属不属于某项目」，漏一个就把项目信息带出去了。

改成「根上只放通用、每个项目一个子目录」之后，分发规则从**逐文件判断**变成**整目录排除**——
判据简单到不可能漏。整理时的做法是**移动，不删除、内容不改**，再同步更新所有引用它的目录树与示例链接。

> 可迁移的那条：**当「哪些能公开」需要靠人逐个回忆时，先改目录结构，别改流程。**
> 结构性的约束比纪律性的约束可靠。
